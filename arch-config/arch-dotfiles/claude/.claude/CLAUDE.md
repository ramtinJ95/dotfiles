RULES THAT SHOULD ALWAYS BE FOLLOWED:
<rules>
  <rule> While scanning code, if anything looks off (bad/dead code, poor naming, refactor opportunity, or VISION misalignment), immediately log a stand-alone entry in `./scratch/BACKLOG.md` so it can be picked up, prioritized, and acted on later. </rule>
  <rule> Always use the researcher agent to fetch up to date documentation that is relevant to the project currently being worked on. </rule>
  <rule> Always try to give suggestions and comparing different solutions and ask the user which one to go with before implementing. </rule>
  <rule> NEVER add yourself as a co-author in git commits. Do not include any "Co-Authored-By" line in commit messages. </rule>
  <rule> Always ask questions when you are not sure or something is not clear. Dont just assume things. </rule>
  <rule> NEVER add comments to the code that just re-explain the function/method name in a more verbose way. </rule>
  <rule> NEVER add comments to obvious variable names etc. </rule>
  <rule> Always prefer more descriptive function/method and variable names over comments. </rule>
  <rule> Using parallel tool calling is MANDATORY. Be proactive about it. DO NO WAIT for the user to request "parallel calls". </rule>
  <rule> If an AGENTS.md file exists in the project root, always read it at the start of each session. </rule>
  <rule> Always do anything that can be done in parallel in parallel without
    waiting for the user to ask for it</rule>
  <rule> No more checkboxes or "generated by" footer in PR descriptions. Keep PR descriptions concise going forward. </rule>
  <rule> When a hook blocks a command (e.g. guard-infra-commands.sh), NEVER self-approve by writing to the approval file yourself. Instead, tell the user what was blocked and ask them how they want to proceed. The approval mechanism exists for the USER to authorize commands, not for you to bypass. </rule>
</rules>
