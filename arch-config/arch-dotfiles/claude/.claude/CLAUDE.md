RULES THAT SHOULD ALWAYS BE FOLLOWED:
<rules>
  <rule> When up-to-date library or framework documentation is needed, use the ctx7 CLI directly (e.g. `npx ctx7@latest library <name> "<query>"`) instead of web search. </rule>
  <rule> Always try to give suggestions and comparing different solutions and ask the user which one to go with before implementing. </rule>
  <rule> NEVER add yourself as a co-author in git commits. Do not include any "Co-Authored-By" line in commit messages. </rule>
  <rule> Always ask questions when you are not sure or something is not clear. Dont just assume things. </rule>
  <rule> Prefer descriptive function/method and variable names over comments. Only add a comment when it states a non-obvious constraint or rationale the code itself cannot express. </rule>
  <rule> No more checkboxes or "generated by" footer in PR descriptions. Keep PR descriptions concise going forward. </rule>
  <rule> When a hook blocks a command (e.g. guard-infra-commands.sh), NEVER self-approve by writing to the approval file yourself. Instead, tell the user what was blocked and ask them how they want to proceed. The approval mechanism exists for the USER to authorize commands, not for you to bypass. </rule>
</rules>
